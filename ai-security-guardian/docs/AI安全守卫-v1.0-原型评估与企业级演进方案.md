# AI安全守卫 v1.0 原型评估与企业级演进方案

> 版本：v1.0 原型评估版  
> 日期：2026-04-29  
> 定位：面向开发升级与后续企业级落地的现状评估文档  
> 结论：当前项目属于企业级安全产品方向的 v1.0 原型 / MVP / 预生产试点基础，尚不等同于完整企业级生产产品。

## 1. 文档目标

本文档用于承接当前 AI-Security-Guardian 的实际代码、文档和本地验证结果，帮助后续开发把项目从“可演示、可试点的原型系统”推进到“可生产落地、可运维、可审计、可持续交付的企业级项目”。

本文档坚持两个原则：

- 不把当前尚未完成的能力包装成已生产可用能力。
- 不低估当前成果：项目已经具备企业级安全平台的主要工程骨架和继续产品化的基础。

## 2. 项目定位

AI安全守卫的产品方向是企业级 AI 安全防护 / SOC 辅助 / 威胁检测与响应平台。它试图覆盖从数据采集、特征提取、模型检测、融合决策、告警运营、响应处置到审计追溯的安全防护链路。

### 2.1 当前成熟度

| 维度 | 当前判断 | 说明 |
|---|---|---|
| 产品方向 | 企业级方向 | AI 安全防护、SOC 辅助、威胁检测与响应均属于企业级安全产品场景。 |
| 工程状态 | v1.0 原型 / MVP | 已有较完整模块，但仍需生产配置、模型可信、测试稳定、真实环境演练。 |
| 交付状态 | 可 PoC / 可内部试点 | 适合演示、答辩、内部验证、dry-run 监控和小范围试点。 |
| 生产状态 | 尚未达到正式生产级 | 不建议直接用于真实生产自动封禁、隔离或阻断核心业务流量。 |

### 2.2 可用边界

当前版本适合：

- 项目评审、课程设计、毕业设计、技术答辩。
- 企业内部 PoC 或安全平台原型验证。
- dry-run 模式下的告警监控、规则验证和响应演练。
- 作为后续企业级产品化开发的工程基础。

当前版本不建议直接用于：

- 面向真实生产业务的自动封禁和自动隔离。
- 对外承诺 SLA、误报率、召回率和合规审计责任。
- 作为独立商业级安全防护产品交付给最终客户。

## 4. 实测验证结论

以下结论来自当前本地环境的验证结果，可作为 v1.0 原型状态的证据，但不等同于生产上线验收报告。

| 验证项 | 结果 | 说明 |
|---|---:|---|
| `scripts/verify_v1.py` | 9 个核心场景通过 | 覆盖正常请求、SQLi、双层 XSS、命令注入、IOC、SYN/异常、模型缺失降级、Redis 降级、审计篡改。 |
| E2E 验收 | 10 passed | 包含 Web 重启后历史告警仍可查询等场景。 |
| 流窗口聚合 | 6 passed | 证明连续流量可形成稳定 flow 特征。 |
| schema/manifest | 7 passed | 模型 manifest 和 schema 基础校验通过。 |
| 生产硬化测试 | 10 passed | 覆盖认证、CORS、默认密钥、Webhook SSRF 等安全硬化项。 |
| 模型治理测试 | 5 passed | ModelRegistry 相关能力通过。 |
| 响应闭环 R4 | 12 passed | 响应动作、调度、通知等基础能力通过。 |
| 性能脚本 | WebAttackDetector P95 约 0.007 ms | 仅代表规则/推理段，不包含真实采集和网络链路。 |
| HTTP 健康检查 | `/healthz` P95 约 26.9 ms | 满足文档中 Web API P95 小于 300 ms 的本地粗测目标。 |

### 4.1 保留风险

| 风险项 | 当前状态 | 影响 |
|---|---|---|
| 全量测试 | `python -m pytest -q` 运行 5 分钟超时 | 不能宣称“全量测试全绿”，上线前必须定位慢测/挂起原因。 |
| 部分分组测试 | 数据库持久化、观测指标相关测试单独运行时出现超时 | 可能与 Redis 探测、后台线程、测试退出清理有关，需要测试治理。 |
| 审计日志 | 当前 `logs/security.log` 已出现哈希链断裂记录 | 生产前必须归档当前日志并重建干净审计基线。 |
| 真实环境 | 当前验证主要在本地环境完成 | 尚未证明真实网卡抓包、真实 Redis、真实响应、TLS/WSS、回滚与备份可稳定运行。 |

## 5. 距离企业级项目的差距

当前项目已经具备企业级方向，但与真正企业级生产项目之间仍存在明确差距。

| 当前状态 | 风险 | 企业级要求 | 后续动作 |
|---|---|---|---|
| `.env` 仍为 `FLASK_ENV=development`，`DRY_RUN=true` | 容易误把开发配置当成生产配置 | 生产配置必须 fail-fast，禁止默认密钥、默认密码和弱隔离 | 增加一键生产配置校验脚本，形成上线前必跑项 |
| 全量 `pytest -q` 超时 | 无法形成完整质量门禁 | CI 中全量测试稳定通过，失败可定位 | 定位后台线程、Redis 探测、慢测依赖，拆分单元/集成/E2E 测试 |
| 审计日志已有断链记录 | 审计证据链不干净 | 生产审计基线必须可校验、可归档、可追溯 | 归档现有日志，重建生产基线，区分测试日志与生产日志 |
| 入侵模型 accuracy 约 75.1%，DDoS 约 91.7% | 误报/漏报风险较高 | 生产模型需达到明确 Precision、Recall、FPR、FNR 指标 | 引入真实数据集、评估报告、灰度发布和模型回滚 |
| 部分模型使用 NSL-KDD 或合成数据 | 数据分布可能与真实生产流量不一致 | 训练数据需贴近目标业务环境 | 建立目标环境样本采集、标注、重训和漂移监测机制 |
| Redis/Guardian/Web 链路本地验证为主 | 真实队列堆积、ack、恢复能力未充分证明 | 需在预发环境验证 Stream 堆积、PEL 回收、断连恢复 | 完成 Redis 压测、断连恢复、consumer 重启演练 |
| 响应能力以 dry-run 为主 | 真实封禁/隔离可能误伤业务 | 自动响应必须有白名单、审批、回滚和审计 | 先进入监控模式，再逐步开放临时封禁和隔离动作 |
| 运维观测仍较基础 | 故障定位和容量判断不足 | 需要指标、日志、告警、巡检、SLO 和容量基线 | 接入 Prometheus/Grafana 或兼容指标平台 |
| 权限模型较简单 | 企业内部多角色协作不充分 | 需要 RBAC、操作审计、最小权限 | 增加角色、权限、操作人、审批流 |
| 集成能力有限 | 难以进入企业现有安全体系 | 需要 SIEM、邮件、Webhook、企业微信/飞书/钉钉、工单系统集成 | 补齐标准集成接口和失败重试策略 |

## 6. 企业级演进路线图

### R1：生产配置与基线整理

目标：让系统能够明确区分开发、测试、预发和生产环境。

关键任务：

- 增加生产配置一键校验命令。
- 固化 `FLASK_ENV=production` 下的强校验行为。
- 明确 `DRY_RUN`、Redis、数据库、模型、密钥、CORS、日志目录的上线要求。
- 归档当前测试日志，重建干净审计基线。

交付标准：

- 缺少生产必填配置时服务启动失败。
- 生产审计日志从干净基线开始，并可通过完整性校验。

### R2：测试稳定化与全量验收

目标：让项目具备可重复、可自动化的质量门禁。

关键任务：

- 修复全量 `pytest -q` 超时问题。
- 拆分单元测试、集成测试、E2E 测试和需要外部依赖的测试。
- 对 Redis consumer、审计巡检等后台线程增加测试退出清理。
- 将 `scripts/verify_v1.py`、E2E、性能脚本纳入验收流程。

交付标准：

- CI 中全量测试稳定通过。
- 慢测和外部依赖测试有明确标签与执行策略。

### R3：模型可信度升级

目标：让检测结果从“可演示”提升到“可评估、可解释、可回滚”。

关键任务：

- 补齐每个模型的 Precision、Recall、F1、FPR、FNR。
- 用目标环境样本或更贴近生产的数据重新训练和评估。
- 建立模型版本、schema、训练数据、指标、发布时间的登记制度。
- 支持模型热更新失败保留旧版本，必要时回滚。

交付标准：

- 每个上线模型都有 manifest 和评估报告。
- 模型指标达到预设生产门槛。

### R4：真实环境部署演练

目标：证明系统在真实部署拓扑中能稳定运行。

关键任务：

- 在预发环境启动 Web/API、Guardian、Redis、数据库。
- 验证真实网卡抓包、Web 日志采集、Redis Stream、告警入库、WebSocket 推送。
- 验证 TLS/WSS、Nginx 反向代理、健康检查、回滚和备份恢复。
- 记录部署手册、演练证据和问题清单。

交付标准：

- 预发环境连续运行稳定。
- Redis Stream 无持续堆积，Web 重启后告警可恢复查询。

### R5：响应闭环治理

目标：让自动响应可控、可回滚、可审计。

关键任务：

- 形成白名单、阈值、审批、定时解封和人工回滚机制。
- 区分 low、medium、high、critical 的响应策略。
- 真实响应动作先以有限范围、低风险策略灰度启用。
- 对误封、响应失败、重复封禁、通知失败形成可见记录。

交付标准：

- high/critical 告警有明确响应策略。
- 所有响应动作有审计记录、状态和回滚路径。

### R6：企业级运维与交付能力

目标：让项目能够被企业运维团队接管。

关键任务：

- 接入指标监控、日志采集、告警通知和巡检任务。
- 补齐上线手册、回滚手册、备份恢复手册。
- 建立版本发布、变更记录和制品管理流程。
- 形成容量基线和核心 SLO。

交付标准：

- 运维团队能独立部署、巡检、回滚和定位问题。
- 关键指标和异常状态可观测、可告警。

### R7：产品化增强

目标：从工程系统走向可持续迭代的安全产品。

关键任务：

- 增加 RBAC、操作审计查询、用户/角色管理。
- 增加企业通知、SIEM、工单、EDR/云安全组等集成。
- 优化告警降噪、误报反馈、报告导出和仪表盘体验。
- 增加多租户或组织隔离能力。

交付标准：

- 满足企业多角色协同、安全运营和合规追溯需求。
- 可按客户环境进行配置化部署和持续升级。

## 7. 上线分级建议

| 级别 | 名称 | 适用范围 | 准入要求 | 当前是否适合 |
|---|---|---|---|---|
| L0 | 演示环境 | 本地演示、答辩、功能展示 | 能启动、能演示核心流程 | 适合 |
| L1 | 内部 PoC | 内部验证、非关键数据、dry-run | 核心场景通过，有基础文档 | 适合 |
| L2 | 预生产监控模式 | 镜像流量、日志监控、只告警不阻断 | 生产配置校验、持久化、基础观测、全链路演练 | 接近，但需补齐 |
| L3 | 有限生产试点 | 低风险业务、小范围自动响应 | 模型评估达标、回滚、白名单、审批、监控告警 | 暂不建议 |
| L4 | 企业级正式生产 | 核心业务生产防护 | SLA、CI/CD、合规审计、完整运维体系、响应治理成熟 | 未达到 |

当前建议评级：**L1 到 L2 之间**。

建议下一阶段先进入 **L2 预生产监控模式**，以真实环境日志和镜像流量验证检测质量，但保持 `DRY_RUN=true`，不直接执行高风险阻断动作。

## 10. 最终结论

AI安全守卫当前不是失败项目，也不是简单脚本或玩具系统。它已经具备企业级安全产品的方向、模块骨架和较多工程化基础，适合作为 v1.0 原型、MVP 或预生产试点基础继续推进。

但从严格的企业级生产标准看，当前项目仍需补齐以下关键能力：

- 全量测试稳定通过。
- 生产配置与审计基线清晰可靠。
- 模型指标达到真实生产要求。
- Redis、Guardian、Web、数据库、TLS/WSS 在目标环境完成演练。
- 响应动作具备白名单、审批、回滚和审计治理。
- 运维监控、CI/CD、备份恢复和企业集成能力完善。

因此，当前最准确的定位是：

> **企业级 AI 安全防护平台方向的 v1.0 原型 / 预生产试点基础。**

后续应以 L2 预生产监控模式为近期目标，以 L3 有限生产试点为中期目标，最终通过模型可信、响应闭环、运维可观测和企业集成能力建设，逐步形成真正可生产落地的企业级安全项目。
