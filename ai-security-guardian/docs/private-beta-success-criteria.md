# AI-Security-Guardian 首批客户私有化 Beta 试点成功标准与退出机制

适用范围：首批单企业私有化 Beta 客户试点  
适用对象：客户项目负责人、客户安全运营、客户运维、DBA、网络/安全团队、交付团队、产品/研发负责人  
默认安全边界：`DRY_RUN=true`，不执行真实封禁、云安全组变更或 EDR 主机隔离

## 1. 试点目标

首批私有化 Beta 的目标不是直接证明正式商用 SLA，而是在客户授权的单企业环境中验证 AI-Security-Guardian 是否具备可部署、可运行、可观测、可审计、可运维、可恢复和可被客户安全团队接受的最小闭环。

试点完成后，双方必须形成以下结论之一：

| 结论 | 含义 | 后续动作 |
|---|---|---|
| 通过 | 核心成功标准达成，无未关闭 P0/P1，无阻断 GA 的客户侧问题 | 可进入扩大试点、商用评估或 Private Deployment GA 准备 |
| 有条件通过 | 核心链路可用，但存在非阻断遗留项 | 明确整改责任人、日期和禁止开启的高风险能力 |
| 不通过 | 核心链路、审计、运维、安全边界或客户接受度未达标 | 暂停试点，按退出机制回滚、整改或终止 |
| 异常终止 | 出现安全、合规、环境或客户决策导致无法继续 | 保全证据，按客户要求备份、移交或清理数据 |

## 2. 试点周期

建议周期为 **2 到 4 周**，按客户环境复杂度选择：

| 周期 | 适用场景 | 推荐安排 |
|---|---|---|
| 2 周 | 环境已准备好，只验证 Web/API、PostgreSQL、Redis、模型、审计和 dry-run 演练 | 第 1 周部署与链路验证，第 2 周运行观察和签收 |
| 3 周 | 需要客户安全运营参与告警研判、误报反馈和通知链路验证 | 第 1 周部署，第 2 周运营试用，第 3 周复验和整改 |
| 4 周 | 启用 full-chain、客户流程复杂、需恢复演练或多轮安全评审 | 第 1 周部署，第 2-3 周稳定运行，第 4 周验收和退出决策 |

试点最短不得少于 10 个自然日；如未达到连续运行观察窗口，不能给出“通过”，只能给出“有条件通过”或“继续观察”。

## 3. 成功指标总览

### 3.1 核心门槛

以下任一不满足，试点不能判定为“通过”：

| 编号 | 门槛 | 通过标准 |
|---|---|---|
| G-01 | 安全边界 | 首批 Beta 保持 `DRY_RUN=true`；如客户要求真实响应，必须另行通过 `--gate real-enforcement` 并附客户书面授权 |
| G-02 | Readiness | 客户目标环境 `python scripts/check_production_readiness.py --gate private-beta` 无 `[FAIL]` |
| G-03 | 核心依赖 | PostgreSQL、Redis、模型目录、配置、审计日志均处于可用状态 |
| G-04 | 健康检查 | `/healthz`、`/readyz`、`/metrics` 可用；`/readyz` 无持续失败 |
| G-05 | E2E 链路 | 演练告警可生成、入库、查询、状态流转、审计留痕和 dry-run 响应记录 |
| G-06 | 安全证据 | 日志和证据包不包含 `.env` 明文、数据库密码、Redis 密码、管理员密码哈希、JWT、API Key 或私钥 |
| G-07 | 问题关闭 | 无未关闭 P0；P1 已关闭或有双方书面认可的规避方案 |

### 3.2 指标类别

| 类别 | 是否必须达标 | 评估方式 |
|---|---|---|
| 可用性 | 必须 | 健康检查、容器状态、客户访问、连续运行记录 |
| 告警链路有效性 | 必须 | 演练告警、Redis Stream、DB、Web 控制台、WebSocket 或替代刷新方式 |
| 审计完整性 | 必须 | 审计哈希链、关键操作审计、审计巡检指标 |
| 运维可执行性 | 必须 | 客户运维独立执行检查、备份、恢复和常见故障定位 |
| 客户接受度 | 必须 | 客户安全/运维/项目负责人签收，确认边界和遗留项 |
| 误报反馈 | 必须 | 建立误报登记、复核、规则/白名单建议和周报闭环 |
| 性能指标 | 必须 | 认证 API、健康端点、检测段或客户约定压测报告 |

## 4. 成功指标定义

### 4.1 可用性

| 指标 | 成功标准 | 证据 |
|---|---|---|
| 连续运行 | 试点最后 7 天内无持续 P0/P1；若试点仅 2 周，至少连续 5 个工作日稳定运行 | 每日运维检查记录、周报 |
| `/healthz` | 每日检查 HTTP 200 | `healthz.json` 或截图 |
| `/readyz` | 每日检查 HTTP 200；DB、Redis、config、models 无 fatal degraded | `readyz.json` |
| `/metrics` | 可被访问或采集，包含 Redis、模型、审计、HTTP 相关指标 | `metrics.txt` 或监控截图 |
| 容器状态 | `app`、`redis` running/healthy；启用 full-chain 时 `guardian` 符合交付边界 | `docker compose ps` |
| 客户入口 | 客户正式 HTTPS 域名可访问控制台；TLS、CORS、WSS/Socket.IO 无阻断问题 | 浏览器截图、`curl -Ik` 输出 |

失败判定：

- `/readyz` 连续 2 个工作日失败且无法恢复。
- Web 控制台不可用超过客户约定窗口。
- DB、Redis 或模型缺失导致核心链路无法验收。

### 4.2 告警链路有效性

| 指标 | 成功标准 | 证据 |
|---|---|---|
| 演练告警生成 | `verify_v1.py`、`staging_drill.py --cleanup` 或客户授权演练场景通过 | 脚本输出、演练报告 |
| Redis Stream | `XLEN`、`XPENDING`、group lag 不持续增长；消费者可正常 ACK | Redis Stream 状态记录 |
| 告警入库 | 演练告警进入 PostgreSQL，Web 重启后仍可查询 | DB 查询、E2E 测试输出 |
| 控制台展示 | Dashboard、Alerts 可查看告警摘要、列表、详情 | 控制台截图 |
| 状态流转 | 告警可进入 investigating/resolved/ignored 等状态，且流转有审计 | 告警历史、审计记录 |
| dry-run 响应 | 响应动作为 `dry_run=true`，结果为模拟执行，不调用真实 provider | response action 记录、dry-run 演练 JSON |

失败判定：

- 演练告警无法进入 DB 或控制台。
- Redis pending/lag 持续增长且无恢复方案。
- Web 重启后历史告警丢失。
- 未经批准出现真实封禁、真实安全组变更或 EDR 隔离。

### 4.3 审计完整性

| 指标 | 成功标准 | 证据 |
|---|---|---|
| 哈希链有效 | `audit_integrity_valid 1`，手工或自动巡检通过 | `/metrics`、hash-chain 校验输出 |
| 关键操作留痕 | 登录、告警状态流转、设置变更、规则/IOC 变更、响应动作均有审计事件 | 审计事件导出或截图 |
| 敏感值脱敏 | 审计和应用日志不记录密码、token、管理员哈希、数据库完整连接串 | 日志敏感信息扫描结果 |
| 审计备份 | 审计日志纳入客户备份或日志归档策略 | 备份清单、SHA256 |

失败判定：

- 审计哈希链失败且无法解释或恢复。
- 关键写操作无审计记录。
- 证据包或日志出现真实敏感凭据。

### 4.4 运维可执行性

| 指标 | 成功标准 | 证据 |
|---|---|---|
| 日常检查 | 客户运维可按运行手册独立执行健康、Redis、模型、审计、磁盘、日志检查 | `customer-beta-ops-checklog.md` |
| 备份 | PostgreSQL、模型、日志、配置 SHA256、镜像 tag、Compose 配置已备份或纳入客户平台 | 备份清单、SHA256 |
| 恢复演练 | 至少完成 1 次隔离恢复演练；如客户周期不足，需签署补做计划 | `customer-beta-backup-restore-record.md` |
| 问题上报 | P0/P1/P2 分级、联系人、升级路径和证据包要求已确认 | 问题单、会议纪要 |
| 回滚路径 | 应用镜像、`.env`、数据库、模型、Redis、误封恢复路径明确 | 回滚记录或演练记录 |

失败判定：

- 客户运维无法按文档完成最小健康检查。
- 无数据库备份或备份不可验证。
- 无 P0/P1 升级路径，发生故障无法止血。

### 4.5 客户接受度

| 指标 | 成功标准 | 证据 |
|---|---|---|
| 使用接受度 | 客户安全运营能完成登录、查看告警、研判、状态流转、查看审计 | 验收截图、操作记录 |
| 边界接受度 | 客户确认 Beta 限制：默认 dry-run、非正式 SLA、真实封禁需另行审批 | 验收签收表 |
| 价值接受度 | 客户认可试点范围内的告警解释、审计留痕、运维流程和下一步价值 | 周报、评审纪要 |
| 责任接受度 | 客户确认主机、网络、证书、DB、Redis、备份介质等客户侧责任边界 | 交付包签收 |

失败判定：

- 客户项目负责人、安全负责人或运维负责人任一明确拒绝签收核心边界。
- 客户认为系统输出不可解释、不可操作且无法通过整改解决。
- Beta 试点能力与客户采购/安全评审预期严重不一致。

### 4.6 误报反馈

| 指标 | 成功标准 | 证据 |
|---|---|---|
| 误报登记 | 所有客户确认误报均记录触发规则、样本、影响、复核人和处理建议 | 问题单、周报 |
| 误报复核 | High/Critical 误报需在 1 个工作日内复核；Medium/Low 误报纳入周报 | 误报处理记录 |
| 调整建议 | 对可解释误报给出规则阈值、IOC、业务白名单或检测范围建议 | 调参建议、变更单 |
| 关闭机制 | 误报关闭前需客户安全运营确认，不直接删除证据 | 告警状态记录、审计 |

参考目标：

- High/Critical 告警误报率应在客户可接受范围内；首批 Beta 不强制承诺固定准确率，但必须能解释、能登记、能复核。
- 同一误报原因连续 3 次以上重复出现，应建立规则调整或白名单计划。

失败判定：

- 误报无记录、无复核、无处置建议。
- 高危误报持续影响客户运营，且无短期规避方案。
- 客户确认存在明显漏报或误报风险，但交付团队无法给出边界说明。

### 4.7 性能指标

默认目标如下；如客户硬件、网络或部署范围不同，可在试点启动会上书面调整。

| 指标 | 成功标准 | 证据 |
|---|---|---|
| 核心认证 API P95 | `< 300ms`，错误率 `< 1%` | `scripts/benchmark_http.py` JSON/Markdown 报告 |
| 健康/观测端点 P95 | `< 300ms`，错误率 `< 1%` | benchmark 报告 |
| 检测段 P95 | `< 100ms` 或客户认可阈值 | `scripts/benchmark_p95.py` 报告 |
| Redis Stream lag | 不持续增长；演练后可回落到 0 或客户认可阈值 | Redis Stream 状态 |
| 页面可用体验 | 登录、Dashboard、Alerts、Settings 无持续超时或 5xx | 手工验收记录 |
| 资源容量 | CPU、内存、磁盘无持续打满；日志和备份分区满足客户保留周期 | 监控截图、运维检查 |

失败判定：

- 核心 API 大量 5xx 或认证 API 无法压测。
- P95 明显超标且无客户书面豁免。
- Stream lag 持续增长导致告警延迟不可接受。
- 磁盘或日志写入风险影响审计、告警或备份。

## 5. 失败与退出条件

### 5.1 必须暂停试点的条件

出现以下任一情况，必须暂停试点并进入问题处置：

| 类别 | 暂停条件 | 首要动作 |
|---|---|---|
| 安全边界 | 未经批准发现 `DRY_RUN=false` 或真实 provider 被调用 | 立即切回 `DRY_RUN=true`，保全响应动作和审计证据 |
| 凭据泄露 | 日志、截图、证据包、聊天或工单出现真实密码、token、私钥、管理员哈希 | 停止传播，轮换凭据，重建证据包 |
| 审计异常 | 审计哈希链失败、关键审计缺失或日志被篡改 | 按 P0/P1 保全现场，暂停非必要变更 |
| 数据风险 | PostgreSQL 迁移失败、数据损坏、备份不可用 | 停止升级，按 DBA 恢复流程处理 |
| 核心不可用 | 控制台、DB、Redis、模型或告警入库持续不可用 | 建 P0/P1，优先恢复链路 |
| 误封风险 | 真实封禁造成或可能造成客户业务阻断 | 止血、解封、加白、复盘，保持 dry-run |

### 5.2 判定为试点失败的条件

满足以下任一条件，试点结论应为“不通过”：

- 试点周期结束时，核心链路仍无法完成演练告警从生成到查询、流转、审计的闭环。
- `/readyz`、Redis、PostgreSQL、模型或审计存在未关闭阻断项。
- P0 未关闭；P1 无客户认可规避方案。
- 客户安全负责人或运维负责人拒绝签收核心边界。
- 敏感凭据泄露后未完成轮换和复验。
- 未经客户书面授权执行真实封禁、云安全组变更或主机隔离。
- 客户前置条件长期无法满足，例如无正式 PostgreSQL、Redis、TLS 域名、部署权限或备份能力。

### 5.3 正常退出

试点达到成功标准后，执行正常退出：

1. 汇总交付证据索引。
2. 关闭 P0/P1，并确认 P2/P3 遗留项。
3. 完成最终健康检查、审计检查、备份检查和性能报告。
4. 双方召开试点评审会，确认通过、有条件通过或进入 GA 准备。
5. 签署试点验收签收表。

正常退出后的可选路径：

| 路径 | 条件 |
|---|---|
| 保留环境观察 | 客户希望继续低风险观察，仍保持 `DRY_RUN=true` |
| 扩大试点 | 成功标准达成，客户希望扩大资产范围、接入更多日志或启用 full-chain |
| 真实响应受控开放 | 必须另行完成真实响应启用申请、白名单、审批、恢复演练和 `--gate real-enforcement` |
| 商用评估 | 客户接受边界、证据齐全、遗留问题不阻断合同评审 |
| Private Deployment GA 准备 | 达成第 6 节转 GA 条件 |

### 5.4 有条件退出

核心链路可用但存在非阻断问题时，可有条件退出。必须在签收表中写明：

- 遗留问题编号、影响、临时规避方案。
- 责任人和计划完成日期。
- 未完成前禁止开启的能力，例如 `DRY_RUN=false`、扩大资产范围、接入真实封禁 provider。
- 是否需要补充恢复演练、压测、误报调优或安全评审。

### 5.5 异常退出

出现以下情况，可异常终止试点：

| 触发条件 | 退出动作 |
|---|---|
| 客户主动要求停止 | 停止服务，按客户要求备份、导出或清理数据 |
| 客户环境长期不满足最低准入 | 暂停部署，保留已生成证据和问题清单 |
| 安全或合规风险不可接受 | 停止试点，轮换凭据，保全审计和问题记录 |
| P0 无法在约定窗口恢复 | 回滚到安全状态，暂停试点复盘 |
| 双方对试点边界无法达成一致 | 形成终止纪要，明确数据处理和责任边界 |

异常退出前至少保留：

- `docker compose ps`、app/redis 日志尾部。
- `/api/health`、`/healthz`、`/readyz`、`/metrics` 输出。
- PostgreSQL 备份文件名和 SHA256 或客户 DBA 备份记录。
- 模型 SHA256。
- 审计完整性校验输出。
- 问题单、变更单和客户终止确认。

## 6. 转 GA 条件

首批私有化 Beta 通过不自动等于 GA。进入 Private Deployment GA 准备前，必须同时满足以下条件：

| 编号 | 转 GA 条件 | 判定标准 |
|---|---|---|
| GA-01 | 至少 1 个首批客户 Beta 完整通过 | 验收结论为“通过”，或“有条件通过”且阻断项清零 |
| GA-02 | 客户目标环境连续稳定运行 | 至少连续 7 天无未关闭 P0/P1，`/readyz` 无持续失败 |
| GA-03 | 交付证据完整 | 交付证据索引中关键项 E-01 到 E-34 已收集或有客户认可的不适用说明 |
| GA-04 | 备份恢复被验证 | 客户环境或等效隔离环境完成恢复演练，RTO/RPO 被记录和签收 |
| GA-05 | 审计可证明 | 哈希链有效，关键操作可查询，审计证据可导出或交付 |
| GA-06 | 性能达标 | 核心 API P95、错误率、Stream lag、页面体验达到客户认可阈值 |
| GA-07 | 运维 SLA 口径明确 | P0/P1/P2 响应目标、维护窗口、升级路径、免责边界和客户责任已形成合同附件草案 |
| GA-08 | 真实响应边界明确 | GA 默认仍为 `DRY_RUN=true`；真实响应作为单独启用包和合同附件 |
| GA-09 | License/授权策略明确 | 私有化授权范围、有效期、节点/用户/保留期/响应能力边界明确 |
| GA-10 | 退出和数据处理明确 | 停用、备份交付、日志归档、数据清理和删除证明流程已成文 |
| GA-11 | Beta 反馈闭环 | P0/P1 全部关闭，P2 有计划，误报和客户体验反馈已转化为任务清单 |

不得转 GA 的情况：

- Redis consumer、审计、数据库迁移、备份恢复、敏感信息保护任一存在未关闭阻断问题。
- 客户验收依赖口头承诺，缺少关键证据。
- 销售或合同承诺包含当前未验证能力，例如正式 SaaS SLA、默认真实封禁、多租户隔离或未演练 HA。
- 真实响应未通过 `--gate real-enforcement` 却被列为默认 GA 能力。
