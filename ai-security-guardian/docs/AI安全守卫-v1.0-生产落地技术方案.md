# AI安全守卫 v1.0 生产落地技术方案

> 版本：v1.0  
> 日期：2026-04-27  
> 定位：面向生产防护系统的技术蓝图  
> 基线：当前代码定位为 v0.8 原型基础，v1.0 目标是在保留现有模块骨架的前提下补齐生产闭环。

---

## 1. 文档目标

本文档基于《AI安全守卫技术架构文档 v1.2》《AI-Security-Guardian Cursor 开发实操指南（安全审查修复版）》以及当前 `ai-security-guardian` 代码实现，描述 AI-Security-Guardian 从原型系统落地为生产防护系统的目标架构、关键能力、部署方式、风险控制和生产化路线图。

本文档不将未实现能力描述为当前已交付能力。凡当前代码未完成的功能，均在“生产化路线图”或“待补齐能力”中说明。

## 2. 当前系统定位

当前代码已经具备完整原型骨架：

| 能力域 | 当前状态 | 说明 |
|---|---|---|
| Web 控制台 | 已有原型 | Flask 页面、REST API、Socket.IO、JWT、CORS、限流均已具备 |
| 数据采集 | 已有基础 | Scapy 抓包、Web 日志解析、系统日志解析、威胁情报查询雏形 |
| 特征工程 | 已有基础 | Flow/Web 特征提取、FeaturePipeline 标准化与编码 |
| 检测引擎 | 已有基础 | DDoS、入侵、Web 攻击、异常检测器均有实现 |
| 融合决策 | 已有基础 | 支持多模型结果融合和等级升级 |
| 防护响应 | 半闭环 | 已有日志、告警日志、iptables 封禁/解封；隔离、限速、真实通知仍需补齐 |
| 审计日志 | 已有基础 | JSON Lines 安全日志、哈希链完整性校验、本地缓冲降级 |
| 部署 | 已有基础 | Dockerfile、docker-compose、Redis、模型只读挂载、非 root 用户 |

当前系统适合作为 PoC、演示系统、毕业设计或内部验证环境。生产 v1.0 的核心目标是把“模块齐全”提升为“检测链路可信、响应闭环可控、状态可持久、运维可观测”。

## 3. 生产 v1.0 目标

生产 v1.0 应达到以下目标：

| 目标 | v1.0 要求 |
|---|---|
| 实时检测 | 网络流量和 Web 日志进入统一检测流水线，端到端检测延迟 P95 小于 100ms |
| 检测可信 | 在线特征 schema、训练特征 schema、模型输入 schema 完全一致 |
| 响应可控 | 告警、封禁、限速、解封、隔离均有审计记录和回滚路径 |
| 状态持久 | 告警、规则、IOC、设置、报告、响应动作持久化到数据库 |
| 安全可审计 | 日志哈希链、操作审计、配置审计、模型版本审计可巡检 |
| 运维可观测 | Redis、Web、Guardian、模型、采集器、队列堆积、检测延迟可监控 |
| 故障可降级 | 模型缺失、Redis 不可用、数据库不可用、单引擎异常不拖垮核心链路 |

## 4. 生产总体架构

```text
                         ┌────────────────────┐
                         │      Nginx/TLS      │
                         │  HTTPS / WSS / ACL  │
                         └─────────┬──────────┘
                                   │
                    ┌──────────────▼──────────────┐
                    │      Web/API 服务            │
                    │ Flask + JWT + Socket.IO      │
                    │ 告警运营 / 规则 / IOC / 报告 │
                    └───────┬──────────────┬───────┘
                            │              │
                 REST/DB    │              │ Redis Streams
                            │              │
             ┌──────────────▼───┐      ┌───▼────────────────┐
             │ MySQL/SQLite      │      │ Redis              │
             │ 告警/规则/IOC/设置 │      │ 队列/缓存/实时事件 │
             └──────────────┬───┘      └───▲────────────────┘
                            │              │
                            │              │
                    ┌───────▼──────────────┴───────┐
                    │       Guardian 检测服务        │
                    │ 采集 / 特征 / 模型 / 融合 / 响应 │
                    └───────┬──────────────┬───────┘
                            │              │
              ┌─────────────▼───┐      ┌───▼──────────────┐
              │ 数据源           │      │ 响应执行层        │
              │ 流量/日志/情报    │      │ 防火墙/EDR/云安全组 │
              └─────────────────┘      └──────────────────┘
```

生产 v1.0 推荐将 Web/API 服务与 Guardian 检测服务拆分运行。Web/API 负责运营交互与持久化查询，Guardian 负责高权限采集、模型推理和响应执行。两者通过 Redis Streams 和数据库共享状态。

## 5. 分层设计

### 5.1 数据采集层

当前已实现 Scapy 抓包、Web 日志增量读取、系统日志解析、AbuseIPDB/VirusTotal 查询基础。

生产 v1.0 应补齐：

- 网络流量入口支持批量读取和滑动窗口，不再逐包直接推理。
- Web 日志入口保留 `src_ip`、`url`、`method`、`status_code`、`response_size`、`user_agent` 等上下文字段。
- 系统日志和应用日志接入异常行为检测链路，覆盖登录失败、异常进程、权限变更、业务异常。
- 威胁情报支持定时同步、TTL、本地持久化和手工导入。

### 5.2 特征工程层

当前已实现 FlowFeatureExtractor、WebFeatureExtractor、FeaturePipeline。

生产 v1.0 的关键要求是特征 schema 统一：

```text
Raw Event -> Normalized Event -> Feature Schema -> Model Input Schema -> DetectionResult
```

必须定义并版本化：

| Schema | 用途 |
|---|---|
| `network_flow_v1` | DDoS、入侵、异常检测的在线流特征 |
| `web_request_v1` | Web 攻击规则和 ML 文本分类 |
| `system_behavior_v1` | 登录、进程、用户行为基线 |
| `ioc_match_v1` | IP、域名、哈希、CVE 命中信息 |

当前 DDoS/入侵检测仍偏向 NSL-KDD 41 维训练特征，而在线流特征只产出部分统计字段。该不一致是生产化路线图的 P0 项。

### 5.3 威胁检测层

当前已有四类检测器：

- DDoSDetector：随机森林模型，依赖模型文件。
- IntrusionDetector：CNN+LSTM 或随机森林模式，依赖 scaler、label encoder、feature columns。
- WebAttackDetector：规则引擎恒可用，ML 模型可选。
- AnomalyDetector：Isolation Forest + Autoencoder。

生产 v1.0 应补齐：

- 模型注册表：记录模型名称、版本、schema、训练数据、指标、发布时间。
- 模型热更新：新模型加载成功后切换，加载失败保持旧版本。
- 模型回滚：按版本回退，并写入审计日志。
- 推理质量回收：记录预测结果、置信度、人工处置状态，用于后续评估。
- 规则前置：IOC、Web 规则、基础阈值先行过滤，降低模型压力。

### 5.4 融合决策层

当前 FusionEngine 已支持多引擎融合和等级升级。

生产 v1.0 应将融合规则配置化：

| 输入 | 决策维度 |
|---|---|
| 检测结果 | threat_type、level、confidence、engine、source_ip |
| 情报命中 | IOC 类型、来源、分数、更新时间 |
| 资产上下文 | 资产重要性、业务分区、白名单 |
| 历史上下文 | 最近告警次数、历史封禁、误报标记 |

融合输出统一为 `DetectionResult`，并进入响应和审计。

### 5.5 防护响应层

当前已实现日志记录、告警日志、iptables 封禁、解封和 dry-run。

生产 v1.0 应形成可控闭环：

| 威胁等级 | 响应策略 |
|---|---|
| low | 仅记录与统计 |
| medium | 告警通知、进入待确认队列 |
| high | 告警、临时封禁、限速、自动解封任务 |
| critical | 告警、封禁、隔离建议或自动隔离、应急通知 |

待补齐能力：

- 邮件、Webhook、企业通知通道。
- iptables 限速和端口封禁。
- 定时解封调度器。
- 主机隔离 API：云安全组、EDR Agent 或堡垒机联动。
- 响应回滚和人工审批。

### 5.6 安全审计层

当前已有 JSON Lines 审计日志与哈希链完整性校验。

生产 v1.0 应补齐：

- 审计事件入库，支持按时间、类型、来源 IP、操作人查询。
- 响应动作、规则变更、登录、配置变更、模型切换全部记录。
- 哈希链定时巡检，异常时发送告警。
- 报告生成基于真实持久化数据，而不是进程内即时聚合。

### 5.7 可视化与交互层

当前 Web 控制台已具备页面、API、JWT、CORS、限流和 Socket.IO。

生产 v1.0 应补齐：

- Web 进程消费 Redis Streams，接收 Guardian 告警并持久化。
- 告警状态流转持久化：open、acknowledged、resolved、ignored。
- 规则、IOC、设置、报告从数据库读取。
- WebSocket 握手鉴权或最小化事件内容。
- 运营页面区分演示数据、真实数据和降级状态。

## 6. 数据流

生产 v1.0 标准链路：

```text
Packet / Log / IOC
  -> Collector
  -> Normalizer
  -> Feature Builder
  -> Rule Pre-filter
  -> Model Inference
  -> Fusion Engine
  -> Response Policy
  -> Audit Log + Database
  -> Redis Stream
  -> Web Dashboard
```

当前代码中 `process_packet()` 逐包调用 `FlowFeatureExtractor.extract([pkt])`，而流特征提取器会跳过少于 2 个包的流并清空状态。生产 v1.0 必须调整为批量/窗口处理，确保流特征稳定输出。

## 7. 部署方案

生产部署推荐：

| 组件 | 部署方式 | 权限要求 |
|---|---|---|
| Nginx | 宿主机或边缘代理 | TLS、访问控制 |
| Web/API | Docker 非 root | 无抓包权限 |
| Guardian | Docker profile 或 systemd | 抓包、iptables 或响应 API 权限 |
| Redis | 内网服务 | 密码、仅内网访问 |
| MySQL | 内网数据库 | 持久化、备份 |
| 日志存储 | 文件 + 数据库 | 追加写、完整性巡检 |

安全要求：

- `SECRET_KEY`、`ADMIN_PASSWORD_HASH`、`REDIS_PASSWORD`、数据库密码、情报 API Key 全部来自环境变量或密钥管理。
- 生产环境禁止使用默认管理员密码。
- 模型目录只读挂载，日志目录可写。
- Guardian 高权限动作必须可审计。
- Redis 不对公网暴露。

## 8. 容错与降级

| 故障 | 降级策略 |
|---|---|
| 模型加载失败 | 保留旧模型；无旧模型时仅规则引擎工作 |
| 单个检测器异常 | 跳过该检测器，其余检测器继续推理 |
| Redis 不可用 | 本地内存降级，恢复后重新连接；生产需记录降级告警 |
| 数据库不可用 | 审计日志写文件，业务写入进入本地缓冲 |
| 情报 API 不可用 | 使用本地 IOC 缓存 |
| 响应命令失败 | 记录失败原因，告警人工处理 |

## 9. 生产化路线图

| 阶段 | 目标 | 关键交付 |
|---|---|---|
| R1 链路可信 | 修复实时流量检测链路 | 批量/滑动窗口流聚合、Web `src_ip` 透传、Redis Stream 消费 |
| R2 状态持久 | 从内存态迁移到数据库 | 告警、规则、IOC、设置、报告 SQLAlchemy 模型 |
| R3 模型可信 | 特征 schema 与模型一致 | schema 版本、模型注册表、热更新、回滚 |
| R4 响应闭环 | 自动响应可控 | 通知通道、限速、定时解封、隔离 API、审批/回滚 |
| R5 运维可观测 | 可生产运行 | 指标监控、日志巡检、CI/CD、性能压测、上线手册 |

## 10. v1.0 验收指标

| 指标 | 目标 |
|---|---|
| 端到端检测延迟 | P95 < 100ms |
| 模型准确率 | Accuracy > 95% |
| 精确率 | Precision > 93% |
| 召回率 | Recall > 95% |
| 误报率 | FPR < 3% |
| Redis Stream 告警消费 | 无持续堆积，消费失败可重试 |
| 审计日志完整性 | 巡检 valid=true |
| 响应动作审计覆盖 | 100% |
| 配置安全 | 生产无默认密钥、无明文默认密码 |

## 11. 结论

AI-Security-Guardian 当前不是失败项目，而是一个结构完整、可继续工程化的 v0.8 原型。生产 v1.0 的关键不是重写系统，而是补齐实时链路、特征模型一致性、持久化、响应闭环和运维观测。完成这些路线图后，系统具备落地为小规模生产防护系统或 SOC 辅助平台的可行性。
